One dataset. Two delivery paths.

The authoring DB and build DB are separate files. In dev there is no build snapshot: Node archive reads use the working DB, while explicit notifications regenerate metadata for both server environments.

Why virtual modules instead of generated JSON?

JSON would work for the small metadata snapshot. Virtual modules are a lifecycle convenience, not a requirement for SQLite or the dev speedup: there is no generated source file to ignore or clean up; Vite asks for fresh module source after explicit invalidation; and builds use the isolated canonical snapshot rather than accidentally reading the working DB.

The archive module also exports functions with a private database path. Generated JSON would still need generation, refresh wiring, and that Node-only archive facade. We keep the virtual modules because they fit this integration, not because JSON would be intrinsically slower.

A successful edit writes a new UUID to tracker.db.revision. Vite invalidates the catalog and its importers in each environment and sends a full reload. The next load regenerates metadata. This file is a notification signal, not a database version or checksum; external SQL requires data:notify after committing its transaction.

What Node’s SQLite module actually does

SQLite is an embedded relational engine. The database is a local file. There is no database server process, network connection, cloud account, ORM, or D1 binding.

Node’s built-in node:sqlite exposes DatabaseSync. Opening a handle, preparing a query and reading rows happen synchronously in the current Node process. That is appropriate for bounded local maintenance and static rendering; it is deliberately excluded from request-serving Workers.

Queries return rows, then domain schemas decode them into plain Season, Team, TeamSeason and Game records. No .data wrappers or framework references. 

import { DatabaseSync } from "node:sqlite";

const db = new DatabaseSync(filename, {
  readOnly: true,
});
try {
  const row = db.prepare(`
    SELECT over_under_twice
    FROM team_seasons
    WHERE season_id = ? AND team_id = ?
  `).get("2025", "CHA");
  // Stored in half-win units: 55 means 27.5.
} finally {
  db.close();
}

Illustration only. Application callers use the guarded archive facade and shared database helpers. Parameters are bound, not interpolated into SQL.

RELATIONSHIPS

Keys, not references

Teams and seasons are parents. Candidate rows join their IDs with odds and display order. Games reference a season and two teams. Historical names have explicit year intervals.

TRANSACTIONS

All or nothing

Write → validate → commit. Failed completeness, asset or integrity checks roll the transaction back. Dev notification follows success, never a failed write.

REPRODUCIBILITY

File for editing. SQL for Git.

Dumps use a read snapshot, primary-key order and escaped literals. Restore validates a temporary file and publishes without overwriting an existing database.

Follow a change through the system

A / EDIT ODDS

Local first

The CLI commits a valid candidate change and writes a revision marker. Vite invalidates metadata in Node and workerd and reloads the browser. Dump, review and rebuild to make preview reflect the change.

B / END A SEASON

Make history explicit

A maintenance command fetches historical NBA rows, pairs scores, checks complete game counts and replaces that season transactionally. After dump/rebuild, wrappers render static UI instead of deferring live data.

C / LIVE RESULT

Nothing writes to SQL

The latest-season action checks date gates and validated KV freshness. It fetches NBA data if needed, updates KV, or serves compatible stale results without an expiry on failure. SQL stays untouched.

External SQL edits need mise run data:notify. Merely saving the file intentionally does not reload metadata. Node archive queries can see committed rows before metadata is refreshed; use notification to return the whole dev view to a consistent revision.

Guardrails that fail loudly

Before data is published

  • STRICT tables, foreign keys, identities and score/odds constraints.
  • Domain checks for dates, candidate cutoffs, historical names, assets and archive completeness.
  • Numbered transactional migrations; no silent missing-DB creation.
  • Actual Git-index dump check—not just a clean-looking working file.

Before code is shipped

  • Environment-aware SQL import/load/transform/build-graph checks.
  • Final artifact inventory and hashes; no database/SQL files in deployment output.
  • No archived game identities in Worker code.
  • Fresh-dump tests, live contract tests and approved historical game/chart golden hashes.

These are architectural safeguards, not a hostile-code sandbox. Lifecycle validation can refuse a build as data ages; it never automatically changes the selected season or archives live data.
