Implementation guide · TanStack Charts 0.18.0 · updated 2026-09-23

What is all this chart code doing?

The chart library supplies the renderer and interaction system. Our code supplies NBA data, the site's presentation rules, and the bridge from Astro's HTML to that library. Those are different responsibilities—and not every compatibility choice we carried over is still necessary.

Three simplifications are now applied, following Zack's approval:

  • Color conversion: the SVG renderer can use CSS variables directly. The legacy one-pixel canvas conversion has been removed.
  • Font waiting: TanStack already invalidates text measurements and redraws when fonts finish loading. Our extra 1.5-second wait is removed; charts render with available fonts immediately.
  • Astro swap cleanup: the app does not currently use ClientRouter. The dormant astro:before-swap listener and its asynchronous disposal scaffolding are removed.

The separate ECharts cleanup at c4635b0 preserved the approved chart bundle and screenshots. This follow-up deliberately simplifies paints and first-font-loading behavior. Delayed successful fonts, failed/stalled fonts, focus, resize and live token changes are covered by browser checks.

1. The rendering flow

  1. Astro wrapper → HTML + data. Each .astro chart wrapper emits a 600px-tall host and a non-executable application/json script. Ordinary bundled JavaScript starts the chart. No React, framework hydration, or client:* directive is involved.
  2. Mount adapter → start at the right time. tanstack.ts reads the payload, waits until the chart is visible or focused, then immediately calls the library's mountChartRenderer. There is no application font wait.
  3. Definition → what the chart means. tanstack-options.ts chooses bars, lines, area fills, rules, scales, labels, data ordering, tooltip content and threshold colors.
  4. TanStack → layout and interaction. The library computes a scene, measures text, handles resizing, keyboard/pointer focus, tooltip positioning, pinning and dismissal.
  5. Our SVG adapter → a few appearance corrections. tanstack-svg.ts limits the background to the plot, removes boundary grid lines, aligns grid strokes, and includes the threshold annotation in every rendered SVG.
  6. Browser → SVG + HTML tooltip. The chart is SVG; the tooltip is ordinary HTML. CSS already supplies the font family, tooltip appearance and keyboard outline.

2. Why are we “recreating” colors?

We are not maintaining a second palette. The values originate in global.css. Today, the JavaScript role map contains direct CSS variable references. The previous conversion pipeline, shown below for context, is removed. 

--color-lime-500: oklch(76.8% 0.233 130.85)
          │ getComputedStyle(root).getPropertyValue(...)
          ▼
       CSS color string
          │ paint one pixel into an offscreen sRGB canvas
          │ read its red / green / blue bytes
          ▼
        #7ccf00
          │ chartTheme: foreground; marks: stroke/fill
          ▼
     SVG paint attributes

That canvas was not drawing the chart. It was a one-pixel color converter. ECharts needed resolved colors because its animation/color parser could not handle our OKLCH strings reliably. During the port I retained the reference's sRGB output to minimize color changes.

That parser restriction does not apply to our TanStack SVG renderer. Its serializer passes paint strings through to SVG. Our current mapping is equivalent to: 

// Direct CSS paint references; no color snapshot or conversion.
const theme = {
  foreground: "var(--color-lime-500)",
  muted: "var(--color-lime-500)",
  grid: "var(--color-lime-200)",
  palette: ["var(--color-green-700)", "var(--color-red-700)"],
};

The mapping is still useful: CSS defines the palette, but cannot infer that eliminated teams are red, the plot is slate, or a below-threshold focus dot should use the brighter red. The conversion is gone. Direct variables follow future CSS theme changes automatically, including existing SVGs, gradient stops and focused dots.

The main cause of the muted text you reported was opacity, not an inability to use CSS colors. TanStack's axis-title/tick defaults were 76%/68%; reference rules defaulted to 50%. Our explicit opacity values override those. Grid rules were already opaque; fractional stroke positioning softened their appearance.

Direct OKLCH and converted sRGB may look identical on your display, or differ slightly through gamut mapping. Removing conversion deserves a visual comparison—not a claim that variables are unsupported, or a promise of a major speedup.

What is already using CSS directly?

  • .chart { font-family: var(--font-mono) }.
  • Tooltip background, text, shadow, padding and font via the library's --ts-chart-tooltip-* properties, mapped to our existing tokens.
  • The lime keyboard outline, tooltip headings, list spacing and image styling.

The new --color-pace-red is a genuinely new accent, not a duplicate palette: the red fill's hue, lime's chroma, and the same +24.1 OKLCH lightness lift that separates the green fill from the lime line. Conversion to sRGB means this is a design starting point, not an exact on-screen contrast-ratio guarantee.

3. Why the font code?

Charts measure text before deciding where to put it. Font choice affects label widths, collisions, tick thinning and whether the final date fits inside the page.

Current: no extra wait

Render using the available font → the webfont arrives → TanStack clears its text-measurement cache and redraws.

Earlier chart visibility, but potentially a second layout and a visible change in label spacing.

Previous: the removed wait

Request regular and bold chart fonts → wait for completion or 1.5 seconds → render with whichever font is available.

Favors stable first layout. Failed fonts are caught; stalled fonts cannot hold the chart indefinitely.

layout.astro already imports Iosevka Curly 400 and 700. The old fonts.ts helper is deleted. It only asked the browser to load those registered faces; it never installed or generated fonts.

Important correction to the original rationale: the library already handles late fonts. In 0.18.0, renderer.js listens for document.fonts.loadingdone, calls domText.invalidate(), and schedules a fresh render. Our former wait was a first-paint policy, not a necessary fix for permanently wrong font measurements.

The wait is now removed. The browser tests hold fonts until the charts render and navigate, then release them successfully and verify native remeasurement, loaded Iosevka, preserved focus, label bounds and resizing. Blocked and indefinitely stalled fonts also leave charts usable. This removes a possible 1.5-second delay—not a measured saving to subtract from every load.

Why specify font sizes and weight in chart options?

Some styling is also layout input. We request 20px bold titles and 16px bold ticks in the definition so the library measures what it draws. Merely forcing font-size or font-weight onto generated SVG text with CSS could make the painted text differ from the measured text.

More inheritance may be possible—the library reads the host's computed typography—but it should be tested as a coordinated simplification. Font family is already inherited. We do not need to duplicate the whole global stylesheet in JavaScript.

4. Why an SVG adapter?

Our accepted design distinguishes the whole chart box from the plotting rectangle:

  • Background: the default theme background covered the entire SVG. We turn that off and insert a rectangle using the scene's exact plot bounds, leaving the gutters transparent.
  • Grid: the default grid uses all scale ticks, including endpoints. We keep endpoint labels but omit grid lines on the plot boundary. This avoids dotted borders.
  • Crisp strokes: interior one-pixel grid lines are placed on half-pixels so they do not split their coverage across neighboring pixels. This changes grid presentation, not data positions.
  • Threshold label and emoji: our annotation is part of the renderer output. Appending it to the DOM only once would be fragile: focus/resize redraws can replace the SVG and erase it.

These are small scene-presentation adjustments, not our own chart engine. Native configuration should replace them if a suitable API becomes available. A CSS shape-rendering experiment might replace explicit grid snapping; that is a candidate to compare, not a verified equivalent.

The pace line and dot

projected wins >= threshold   → lime line / lime focus dot
projected wins <  threshold   → bright red line / bright red focus dot

one continuous smoothed path
    + hard SVG gradient stop at the threshold
    = exact color crossing, without splitting or duplicating games

The line gradient uses the line's own bounding box. For example, top 82, bottom 18, threshold 38 gives a stop of (82 − 38) / (82 − 18) = 68.75% from the top. Flat and one-sided lines use solid colors.

The dot needs its own per-row color rule. Reusing the path gradient on a small circle would apply that gradient to the circle's bounding box, potentially splitting the dot into two colors. Instead, a native focusGuideX marker uses the original row's projected wins to select one fill and outline color. TanStack still handles the pointer and arrow keys.

5. Mounting, focus and astro:before-swap

Mounting is mostly integration glue

  • Visibility or focus starts the chart. Lazy mounting avoids doing every chart's layout immediately. Keyboard focus also triggers it, so an offscreen/unmounted chart is not inaccessible.
  • One tab stop. Before mounting, the host is the loading target. After mounting, the SVG owns focus. If the user is on the loading host, we transfer focus immediately. Visibility-triggered mounting does not steal focus from elsewhere.
  • One instance. The mounted flag prevents visibility and focus events from creating duplicate charts.
  • Visible failure. Mounting failures get an alert message instead of a silently empty chart.
  • Native tooltips. We supply safe DOM content using the original row; the library handles placement, navigation and dismissal. The helper names node, add and logo are conveniences, not requirements of TanStack.

The focus outline belongs to the host via .chart:has(svg:focus-visible). Stats deliberately clips descendants to prevent tooltip overflow; an outline on the SVG itself was clipped away. That CSS solves an actual reviewed defect without adding another keyboard controller.

What the Astro event means

astro:before-swap is emitted by Astro's client-side router before it replaces the old page DOM during a client navigation. The JavaScript document survives that kind of navigation.

ClientRouter navigation

Old DOM → before-swap → destroy old chart/listeners/observers → replace DOM → initialize new charts.

Explicit cleanup matters because the document and its listeners survive.

This app today

Normal page navigation → browser loads a new document. No ClientRouter is present.

The dormant before-swap listener is removed. The old page is discarded or preserved together in the browser's back/forward cache.

The former handler disconnected the observer, removed the loading-focus listener, called TanStack's destroy(), and marked pending asynchronous work as disposed. With no client router or asynchronous font wait, that scaffolding no longer serves the current app.

Applied: the dormant router branch is removed. If we add ClientRouter later, we need a complete lifecycle plan—including initializing new pages, not just destroying old charts. The old listener alone did not make the adapter client-router-ready. It is not a general hook for every Astro update, server island, resize or ordinary page unload.

6. What earns its keep?

Piece Assessment Why

Marks, scale domains and data ordering Keep These define the chart's meaning. Explicit configured scale instances prevent the domain/color reinference observed with factories.
Semantic palette mapping Kept with direct CSS references The library needs to know which token serves each role. The values can be CSS variable references.
One-pixel color conversion Removed Legacy parser/parity history, not an SVG requirement. Check gamut and screenshot differences.

Axis sizes, bold weight, opacity Keep layout and paint in sync Override unsuitable defaults without making measured text disagree with CSS-painted text.
Plot-only backdrop, interior grid, annotation Keep for the accepted design Concrete differences from default rendering. Prefer simpler native/CSS replacements only after proving equivalence.
Lazy mount and focus transfer Keep unless intentionally going eager Useful loading policy plus correct keyboard entry. Not a second interaction controller.
before-swap handler Removed No ClientRouter. Revisit lifecycle handling alongside actual client navigation support.
Tooltip DOM builders and image alternatives Keep the safety/content contract Library defaults cannot know our team history, logos or descriptions. Helper organization can be simplified.
Generic TypeScript parameters Compile-time safety Link each chart's rows and axes to tooltip/focus callbacks. They add no runtime JavaScript.

This pass is complete: direct CSS paints, synchronous mounting with native font recovery, and no dormant router branch. Explicit axis metrics, native interaction and the small SVG presentation adapter remain. This is separate from the earlier ECharts deletion.

The application, tooltip-safety and expanded font-resilience harnesses cover delayed successful loading as well as blocked/stalled fonts, keyboard focus, narrow label bounds, both line/dot colors and live CSS token changes. Normal settled screenshots retain their geometry; the direct-color change produces at most one RGB channel step (out of 255) in the checked Chrome captures. No new startup-speed claim is made.

What was checked in the pinned library and Astro source?
  • @tanstack/charts/dist/renderer.js: the loadingdone listener, text-cache invalidation, scheduled redraw and destroy cleanup.
  • dist/dom-text.js: reads host computed typography and uses canvas text measurement. This is separate from our removed color-conversion canvas; the displayed chart remains SVG.
  • dist/svg.js and dist/svg-renderer.js: paint strings pass through to SVG attributes; known gradient URLs get ID scoping.
  • dist/scene.js and dist/rule.js: the background/grid generation and opacity defaults.
  • astro/dist/transitions/events.js and router.js: before-swap belongs to client navigation. Application source contains no ClientRouter or ViewTransitions component.

These findings apply to the currently pinned versions, not a promise about every future TanStack release or another rendering backend.
