NBASTT

Portable Image Service

An Astro image service for Cloudflare-deployed sites that makes <Image> behave the same whatever the file type, without depending on paid Cloudflare image infrastructure. Specced for a later agent to implement; nbastt is the test case, not the beneficiary.

01

Why this exists

Zack's sites deploy to Cloudflare. The premise here is not that the adapter has a bug — it is that no single setting on @astrojs/cloudflare makes every image type work without paying Cloudflare. Getting this site's images working in build and at runtime took two coordinated overrides, and the zero-config default was unusable for a site whose assets are all SVG.

What the default actually does: with no imageService set, normalizeImageServiceConfig resolves "cloudflare-binding", which yields transformAtBuild: false and needsImagesBinding: true. Every runtime image request goes to env.IMAGES — so rendering a logo requires provisioning Cloudflare's metered Images product first, whether or not any pixel needs touching. verified @astrojs/cloudflare@14.3.0 — dist/utils/image-config.js:2-17 and dist/index.js:87-89

imageService Endpoint in dev Endpoint at runtime Needs paid binding
cloudflare-binding (default) transform transform yes
compile transform passthrough no
passthrough generic passthrough no
cloudflare generic CF service yes

verified @astrojs/cloudflare@14.3.0 — dist/utils/image-config.js:28-77, reading setImageConfig branch by branch. "transform" is @astrojs/cloudflare/image-transform-endpoint, which calls env.IMAGES.

!

The bolded cell looks like an adapter bug, and it is the one we papered over by hand. Under compile the runtime service is passthrough, yet command === "dev" hardcodes the Cloudflare Images endpoint anyway — the adapter routes dev at a product its own configuration says nothing should reach. The passthrough and cloudflare branches immediately above it both special-case dev to GENERIC_ENDPOINT; compile does not. One line, mirroring its neighbours, would make the Step 8 dev shim unnecessary for everyone. Worth filing upstream. verified dist/utils/image-config.js:31-63

The SVG failure itself is a second, narrower fact: the transform endpoint's accepted output formats are a hardcoded jpeg, jpg, png, gif, webp, avif, so an SVG request returns 400 Unsupported format: svg. verified dist/utils/image-binding-transform.js, the supportedFormats map inside transformStream That is stricter than the platform it wraps: Cloudflare Images lists SVG as both a supported input and output format, states that it does not resize SVG and ignores optimization parameters for it, and sanitizes it with svg-hush on delivery. verified developers.cloudflare.com/images/get-started/limits/ and blog.cloudflare.com/svg-support-in-cloudflare-images/

Both facts land on the same DX complaint, which is the actual motivation: you have to know a file's type, and hold a matrix of adapter settings in your head, to know whether you may use Astro's <Image> component. That is a bad seam to carry across several personal sites. The goal is one service that makes <Image> simply correct for every format, on Cloudflare, with no paid image product involved and no per-site configuration archaeology.

Goals

  • <Image> and getImage() work for SVG and raster alike, with no per-call-site knowledge of type.
  • No Cloudflare Images binding, no metered transformations, no account provisioning.
  • SVG emits one file per source, not one per requested size. Sizes are meaningless for vectors.
  • Raster keeps sharp-quality output at build time.
  • Raster transformation still works at runtime inside workerd, for server islands and on-demand routes.
  • Optional: a build-time audit that flags SVGs carrying unsafe features.

Non-goals

  • Runtime SVG rasterization. Vectors go out as vectors.
  • Replacing sharp at build time. Sharp is better than anything that runs in workerd and it already works in Node.
  • Remote-image handling beyond what baseService already does.
i

nbastt is the test case, not the customer. This site is 100% SVG and currently uses a plain <img src={meta.src}>, which is strictly less machinery than any service. Landing the service here proves it; the payoff is the other sites. Do not remove the <img> approach until the service is verified against it.

02

How Astro's image pipeline actually works

This is the part that makes the design possible, and it is not obvious from the docs. All of it was read out of astro@7.3.1 and @astrojs/cloudflare@14.3.0 as installed in this repo.

Service and endpoint are two different things

image.endpoint
The route that serves /_image. An Astro API route.
image.service
The module that does the pixel work. Called by that route at runtime, and by the build when generating static images.

The adapter's imageService option is a preset that sets both. Under "compile" in dev it pairs a passthrough service with the Cloudflare binding endpoint — which is why SVG broke in dev while the build was fine. verified @astrojs/cloudflare dist/utils/image-config.js, setImageConfig, the compile case

A user service survives compile, and runs in Node

Two facts that together make this whole design work. First, setImageConfig's compile branch keeps a user-set service rather than overriding it: 

service: hasUserImageService(config) ? config.service : WORKERD_IMAGE_SERVICE

Second, at build the adapter imports that entrypoint in Node to generate the static images: 

if (userImageServiceEntrypoint) {
  const mod = await import(userImageServiceEntrypoint);
  globalThis.astroAsset.imageService = mod.default ?? mod;
} else {
  const { default: sharpService } = await import("astro/assets/services/sharp");
  globalThis.astroAsset.imageService = sharpService;
}

verified @astrojs/cloudflare dist/prerenderer.js, around lines 188 and 241

So transform() runs in Node at build time with sharp available, and in workerd only when /_image is hit at runtime. The service must therefore branch on runtime, and must never import sharp at module top level or the worker bundle breaks.

Variant filenames, and how to collapse them

Astro does not statically analyse anything. Every <Image> / getImage() call at render time calls addStaticImage(), which hashes the transform props and accumulates them in a global map; after all pages render, the build writes one file per accumulated hash. The filename is <base>_<hashTransform(...)><ext>. verified astro dist/assets/vite-plugin-assets.js addStaticImageFactory; dist/assets/utils/hash.js propsToFilename, hashTransform

On this site that produced 98 files from 45 sources, every one byte-identical to its source, because a logo used at five sizes got five hashes. propertiesToHash is a static string[] on the service, so it cannot be varied per image — but validateOptions runs before the hash, and its return value is what gets hashed: 

const validatedOptions = service.validateOptions
  ? await service.validateOptions(resolvedOptions, imageConfig, logger)
  : resolvedOptions;
// …then, further down…
globalThis.astroAsset.addStaticImage(validatedOptions, propsToHash, originalFilePath)

verified astro dist/assets/internal.js, lines ~132 and ~158-161

That is the hook. Strip the size props off an SVG in validateOptions and every call site collapses to one hash, hence one file.

03

Design

One service module implementing Astro's LocalImageService, spreading baseService and overriding four methods.

validateOptions — collapse SVG variants

If the source is an SVG, delete width, height, quality and any format other than svg from the returned options, after stashing the dimensions somewhere outside propertiesToHash. Everything else passes to baseService.validateOptions untouched.

!

getHTMLAttributes receives the validated options, so stripping width/height there would also strip them off the rendered <img> and reintroduce layout shift. The stash-and-restore is not optional. Astro's baseService.getHTMLAttributes derives targetWidth/targetHeight via getTargetDimensions(options) — read it before writing the override.

getHTMLAttributes — restore them

Read the stashed dimensions back and emit width/height exactly as baseService would have. Callers that pass only a width must still get a height derived from the source aspect ratio; result-emoji.astro in this repo shows the arithmetic.

transform — branch on type, then on runtime

Input Build (Node) Runtime (workerd)
SVG svgo, return as svg Return input unchanged, image/svg+xml
Raster sharp, lazily imported inside the call jSquash wasm codecs (see §4)

Runtime detection: prefer a build-time flag injected by the companion integration over sniffing globals, so the branch is statically analysable and the unused side can be tree-shaken out of the worker bundle. unverified — confirm Rolldown actually drops the sharp branch; if it does not, split into two entrypoints and let the integration choose.

What not to touch

getURL and parseURL inherit from baseService unchanged. Do not reimplement them; the adapter's endpoints parse those URLs.

svgo lives here

This repo currently runs svgo from a separate astro:build:done integration (svg-optimizer/integration.ts), because with plain <img> the image pipeline never sees these files. Once the service is in, svgo belongs in transform() instead and that integration should be deleted. Note svgo v4 dropped removeViewBox from preset-default; do not add it back, these logos are rendered at several sizes. verified svgo 4.1.0 warns "removeViewBox is not part of preset-default"; measured 113,401 → 78,211 bytes over this site's 45 SVGs

04

Raster at runtime in workerd

This is the piece that justifies the whole exercise being "portable" rather than "an svgo wrapper," and it is more viable than it first appears.

jimp's wasm codecs are real

@jimp/wasm-webp and @jimp/wasm-avif both exist at 1.6.1. They are opt-in plugins, which is why they are absent from the default jimp dependency list. @jimp/wasm-webp is a thin wrapper over @jsquash/webp — the Squoosh codecs. verified npm pack @jimp/wasm-webp 1.6.1 → dist/esm/index.js imports @jsquash/webp/decode.js and /encode.js

workerd blocks dynamic wasm, jSquash has the escape hatch

Workers disallow WebAssembly.instantiate() on an ArrayBuffer — "Wasm code generation disallowed by embedder." A .wasm file must be statically imported so the runtime hands you a WebAssembly.Module. verified developers.cloudflare.com/workers/runtime-apis/webassembly/

jSquash's init() takes exactly that, and its README names Cloudflare Workers as the reason: 

export async function init(module, moduleOptionOverrides) {
  let actualModule = module;
  // …if only one argument and it is not a WebAssembly.Module, treat it as options…
  emscriptenModule = initEmscriptenModule(webp_dec, actualModule, actualOptions);
}

verified npm pack @jsquash/webp 1.5.0 → decode.js; README §"Usage in Cloudflare Workers"

So the runtime path is:

import WEBP_ENC_WASM from "@jsquash/webp/codec/enc/webp_enc.wasm";
import encode, { init as initEncode } from "@jsquash/webp/encode.js";

initEncode(WEBP_ENC_WASM);

Bundle budget

Each codec is a separate binary and they are not small. Measured from the packed tarballs:

File Size Needed for
webp_dec.wasm 135 KB reading WebP sources
webp_enc.wasm 275 KB writing WebP
webp_enc_simd.wasm 337 KB faster writing; pick one

Workers limits are 3 MB compressed on the free plan and 10 MB on paid, so a webp encoder alone is affordable, but shipping the full jimp plus every codec is not obviously so. zack decides — which formats are worth carrying in the worker at all? A defensible default is WebP encode only, with anything else passed through unchanged at runtime.

!

The unresolved risk. @jimp/wasm-webp's own wrapper calls jSquash's init() with no module, letting jSquash resolve the binary itself — which is the thing workerd forbids. Priming the same module instance by calling init(WASM_MODULE) first should work, because the plugin imports the same singleton, but that is inference from reading the source, not a test. unverified

Verify this before building anything else. The cheapest probe: a throwaway Worker that statically imports webp_enc.wasm, calls initEncode, and encodes a 2×2 pixel buffer. If that fails, drop jimp and call jSquash directly — jimp's value here is only its resize/decode plumbing.

×

Correction to earlier advice. An earlier pass told Zack jimp had no WebP or AVIF support and could not run in workerd. Both claims were wrong: the codecs exist as separate wasm packages, and jSquash exists specifically to run in Workers. The design here follows Zack's original instinct.

05

SVG safety audit

The use case is not sanitizing untrusted uploads. It is auditing assets Zack pulls into projects — SVGs generated elsewhere, downloaded, or modified from other sources — where an unsafe feature is easy to overlook. That makes this a build-time lint, running in Node, not a runtime sanitizer. A reasonable shape: fail the build when an SVG carries features outside an allowlist, unless that file is explicitly allow-listed.

What svg-hush is

Rust crate, version 0.9.7, Apache-2.0 or MIT. Removes scripting, cross-origin hyperlinks and cross-origin resource references; strips anything outside its allowlist; forces URLs same-origin. It has a src/main.rs, so the crate ships a CLI as well as a library. Its dependencies are all pure Rust — data-url, base64, quick-error, url, xml — with no C or system libraries, which is what makes a wasm32 build plausible. verified github.com/cloudflare/svg-hush — Cargo.toml, README.md, src/ listing

!

It cleans; it does not report. The public API is Filter::new() and filter(read, write) — cleaned bytes out, no list of what was removed. So "flag unsafe features" has to be implemented as filter, then compare against the original: unequal means something was stripped. That tells you a file is dirty but not why, so any failure message should include a diff or point at the file for a human to inspect. verified src/lib.rs — the impl Filter block

Ways to call it from Node

Option Cost Verdict
cargo install svg-hush, exec the CLI Rust toolchain on every dev machine and in CI; process spawn per file Best first step. Zero new npm dependencies, first-party code, and it proves the idea before anyone builds packaging.
Build it to wasm yourself (wasm-pack) A small wrapper crate and a release pipeline; you own the artifact The right long-term answer if the lint earns its keep. Works in Node and workerd. Dependencies are pure Rust, so it should compile clean. unverified
napi-rs native addon Per-platform prebuilds, CI matrix, binary distribution More work than wasm for no benefit — this only ever needs to run in Node at build. Skip.
@zeropress/svg-hush (third-party wasm) v0.1.0, single maintainer, published 2026-08-19 Against this project's strict pnpm supply-chain posture. Useful as a reference for how to build the wasm, not as a dependency.
Port the allowlist to JS Ongoing drift against upstream; you own the security judgement Tempting since svgo already parses SVG, but the allowlist is the product. Don't fork it.

zack decides Ship this as part of the image service, or as a standalone lint that runs from lefthook over src/assets? The lint has no dependency on the service and is useful on its own — arguably it should land first, since it is smaller and the value is immediate.

06

Package shape

Built for reuse across Zack's Cloudflare sites, so it wants to be its own package, developed here and extracted once it works. Look at ~/proj/grepco/opensource/pagemeta for his house conventions on packaging, since that is where the pnpm and tooling preferences in this repo came from.

./service
The image service. Set as image.service.entrypoint. Must not import sharp at module scope.
./integration
An Astro integration that wires the service, injects the runtime flag, and (optionally) runs the SVG audit. Ordering matters: Astro unshifts the adapter to the front of config.integrations, so any user integration's updateConfig merges on top of the adapter's. verified astro dist/integrations/hooks.js, lines 127-129 in runHookConfigSetup
./endpoint
Optional. Only needed if the adapter's own endpoints prove unsuitable; prefer not shipping one.

Consumer config should end up roughly:

adapter: cloudflare({ imageService: "compile" }),
image: { service: { entrypoint: "<pkg>/service", config: { formats: ["webp"] } } },
integrations: [cfImages({ auditSvg: true })],

imageService: "compile" is load-bearing: it is the mode whose hasUserImageService check preserves a user-set service and whose build path imports it in Node. "custom" also respects a user endpoint but logs a permanent, false "Sharp image service cannot run inside the workerd runtime" warning on every dev start. verified dist/utils/image-config.js — the custom case's logger.warn

07

Milestones and verification

Strictly ordered — each one kills the project cheaply if it fails.

  1. Probe wasm in workerd. Throwaway Worker, static webp_enc.wasm import, encode a 2×2 buffer. If this fails, §4 is dead and the service degrades to "sharp at build, passthrough at runtime" — still worth building, but stop and re-scope with Zack first.
  2. Variant collapsing. Service that only overrides validateOptions and getHTMLAttributes, spreading baseService otherwise. Revert this site to <Image> and confirm the build emits 45 SVGs, not 98, with width/height intact on every <img>.
  3. svgo into transform(). Delete svg-optimizer/integration.ts. Confirm total SVG bytes land at ~78,211 as the standalone integration achieves today.
  4. Raster at build. Add a real PNG to this site and confirm sharp still converts it (a 400×400 PNG went 3,265 B → 100 B WebP under the stock adapter; match that).
  5. Raster at runtime, per the §4 probe.
  6. SVG audit, per §5.
  7. Extract the package.

Acceptance criteria, using this repo's harness

Everything under plan/baseline/; see its README. The bar is the existing runs, not a fresh eyeball.

  • capture.mjs + compare.mjs against runs/2026-09-11-svgo: 44/44 screenshots within the 1–5px antialiasing noise already documented there, 0 console errors.
  • Server islands on real workerd via astro preview with a scratch 2026 team season — one 2026/CHA entry at overUnder: 30.5, which is what runs/2026-09-09-astro-7-scratch-island used. Getting this wrong produces an 11% diff that is nothing but different data.
  • dev-smoke.mjs exits 0 with 47 images across seven pages. Required — this whole area shipped broken once because every check ran against built output.
  • astro check, ESLint (--flag unstable_native_nodejs_ts_config), prettier, and pnpm test all clean.

Open questions for Zack

  1. Which raster formats are worth carrying in the worker bundle? WebP encode only is the cheap default; every added codec is 135–337 KB.
  2. Does the SVG audit ship inside this package, or as a standalone lefthook lint? It has no real dependency on the service.
  3. Is a Rust toolchain acceptable as a build prerequisite, even temporarily? That decides whether milestone 6 starts with the svg-hush CLI or goes straight to building a wasm artifact.
  4. Where does the package live — its own repo, or a workspace alongside pagemeta?
  5. Does <Image> come back to this site once the service works, or does nbastt stay on plain <img> and serve only as the test bed? The <img> approach is genuinely less machinery for a site with no raster images.
